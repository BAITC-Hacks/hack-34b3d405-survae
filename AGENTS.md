# SURVAE: правила совместной разработки

Ты работаешь в команде из трёх участников, а не над отдельной версией сайта.
Чужие чаты и незапушенные файлы тебе не видны. Не утверждай обратное.

## Перед работой

1. Прочитай `docs/TEAM_CONTEXT.md`, свою роль в `docs/TEAM_PROMPTS.md`,
   `docs/FRONTEND_API.md` и `docs/TEAM_WORKFLOW.md`.
2. Проверь `git status`, текущую ветку, remote и HEAD. Не трогай чужие изменения.
3. Уточни роль, если пользователь её не назвал. Покажи роль, задачу, базовый SHA,
   разрешённые файлы и критерий готовности до редактирования.
4. Получи свежую информацию о main и открытых PR. Если доступа нет, сообщи об этом;
   не называй локальную версию актуальной без проверки.

## Границы

- Участник 1 / INTEGRATOR: приёмка, `tests/test_acceptance_*.py`, общие документы,
  очередь PR. Не меняет app/ и static/ без согласования владельца.
- Участник 2 / BACKEND: `app/`, `data/`, backend-тесты, контракт API и зависимости.
- Участник 3 / FRONTEND: `static/`, frontend-тесты. Не переносит API-ключ в браузер.
- Чужую область не переписывай: предложи изменение через PR/комментарий и согласуй.
  Изменение формата API требует согласия backend и frontend до реализации.
- Работай в отдельной ветке от свежей main. Не заменяй проект архивом целиком.
  Не используй force push и destructive reset; не меняй настройки репозитория.
- Объединение PR выполняет интегратор после проверок и разрешения пользователя.
  Эти правила не дают сами по себе права пушить, создавать ключи или делать деплой.

## Неприкосновенные условия продукта

- Цена, остаток, сертификат и совместимость — из данных каталога, не выдумка модели.
- Три метода сохраняются: POST /api/chat, POST /api/cart/confirm, GET /api/cart.
- Чат и AI не меняют корзину напрямую. Нужны proposal_id и confirmed:true.
- Повтор подтверждения не дублирует заказ; сессии изолированы; CSRF не отключать.
- Demo, live и fallback различать явно. Не выдавать демо-корзину за заказ ekt.kz.
- Не читать/печатать/коммитить `.env`, API-ключи, cookie или секреты команды.
  Для диагностики выводи только факт наличия настройки, не значение.

## Перед передачей результата

- Прогони `python -m pytest -q`; JS: `node --check` для изменённых файлов.
- Для интерфейса проверь сценарий в браузере, не только синтаксис.
- Платные live-проверки — только в рамках согласованной задачи, коротко и без секретов.
- Передай: задача, ветка/commit/PR, изменённые файлы, проверено/не проверено,
  влияние на API, следующий шаг. Не называй работу готовой только потому, что она написана.
- Ссылки и результаты в GitHub — общая память. Отчёт в личном чате её не заменяет.
