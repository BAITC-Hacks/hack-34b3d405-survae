## Замечания к BE-01

### BE01-R1 / P2 — вопрос о минимальной партии перехватывает подбор лампы

1. В новом диалоге отправить `Лампа E27 до 40 Вт 3000 К`.
2. Убедиться, что выбран `DEMO-LED-W`.
3. Спросить `Какая минимальная партия?`.

Факт: ассистент повторяет «совпадают три указанных параметра» и карточку лампы.
Ответа на вопрос об условиях покупки в сообщении нет. В карточке значение партии
показано, но существующий обработчик коммерческого вопроса не вызывается.
Ожидается содержательный ответ о минимуме выбранной позиции по каталогу.
Корзина в обоих случаях остаётся пустой.

Причина: [app/lamps.py, строка 100](https://github.com/BAITC-Hacks/hack-34b3d405-survae/blob/8c5d02d2c824b060151eb54623a7aceb09783f8c/app/lamps.py#L100)
пропускает доставку, оплату, сертификаты и аналоги, но не вопрос о минимальной
партии. Активный lamp-контекст забирает его раньше общего обработчика.
Это затрагивает must-have №3 официального кейса. Воспроизведено через API и UI.

Тест: `test_minimum_order_question_after_lamp_selection`.
Исправление — область BACKEND; после него проверить и ответ, и сохранность
ламповых параметров при возвращении к подбору.

### BE01-R2 / P2 — точная мощность превращается в верхнюю границу

Последовательность сообщений в новой сессии:
`Нужна лампочка` → `E27` → `Нужна ровно 40 Вт` → `3000 К`.

Факт: возвращается `DEMO-LED-W` мощностью **9 Вт**, а текст сообщает
«не более 40 Вт». Явное «ровно» теряется. В demo нет лампы E27 40 Вт 3000 К;
ожидается отсутствие точного совпадения либо уточнение, без выдачи 9 Вт за
совпадение. Корзина остаётся пустой.

Причина: [app/lamps.py, строка 42](https://github.com/BAITC-Hacks/hack-34b3d405-survae/blob/8c5d02d2c824b060151eb54623a7aceb09783f8c/app/lamps.py#L42)
выбирает `max` для любого ответа на шаге `awaiting=power`, даже при явном точном
ограничении. Проверка точной мощности в одном сообщении не покрывает этот
многошаговый случай. Воспроизведено через API.

Тест: `test_exact_wattage_reply_never_becomes_a_maximum`.
Исправление — область BACKEND; явное точное условие должно иметь приоритет
над подразумеваемым пределом из предыдущего вопроса.

## Воспроизведение дополнительных проверок

В чистой рабочей копии репозитория с доступом к origin, в новом соседнем worktree:

```bash
git fetch origin
git worktree add --detach ../survae-qa-be01-fe01 8c5d02d2c824b060151eb54623a7aceb09783f8c
cd ../survae-qa-be01-fe01
git merge --no-commit --no-ff 37c5901413675a307e83e6013b1501b9f33a6479
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
node --test tests/frontend_flow.test.cjs
git show origin/qa/case-review:tests/test_acceptance_case.py > tests/test_acceptance_case.py
git show origin/qa/case-review:tests/test_acceptance_be01_review.py > tests/test_acceptance_be01_review.py
python -m pytest -q tests/test_acceptance_case.py tests/test_acceptance_be01_review.py --runxfail
```

Последняя команда намеренно возвращает ненулевой код: **1 passed, 3 failed** на
указанных SHA. Это локальная диагностическая сборка, её не коммитить и не пушить
как merge в main. На Windows команды создания/активации `.venv` — из README.

Тест лампы QA-01 уточнён: добавлена мощность «до 40 Вт», чтобы проверять все три
явных параметра. Вопрос о недостающей мощности в исходном запросе без неё допустим.
При будущей интеграции BE-01 снять с этого исправленного теста старый strict-xfail;
иначе он выдаст XPASS(strict). Новые strict-xfail отмечают известные ошибки,
а не прохождение требований; после исправлений соответствующие маркеры удалить.

  Пятиминутный срок предложения покрыт unit-тестом, вручную не выжидался.
- **PR #6:** вернуть владельцу BE01-R1/R2, затем повторить воспроизведения.
- **PR #5:** в проверенном объёме блокирующих ошибок не найдено; после изменений
  backend снова выполнить общий сценарий на точных head обоих PR.
- **PR #7:** хранит QA-матрицу, этот отчёт и воспроизведения; не означает merge
